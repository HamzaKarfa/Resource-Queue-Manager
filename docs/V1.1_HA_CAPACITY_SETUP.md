# Resource Queue Manager v1.1 — Home Assistant capacity configuration

**Release:** the described Home Assistant capacity options are included in **Resource Queue Manager v1.1.0 stable**, following the validated [v1.1.0-rc.2](https://github.com/HamzaKarfa/Resource-Queue-Manager/releases/tag/v1.1.0-rc.2).

## Setup and options

From Settings → Devices & services → Resource Queue Manager:

During **new queue setup**, choose supervised entities, then capacity (Classic 1–50 slots or Weighted 1–100000 shared units), scheduling and allocation (Strict/Backfill), recurrence, and any required strategy fields or per-entity default weights. Weighted mode shows one native numeric default-weight field per supervised entity, initially 1.

To change an existing queue, open **Configure** and choose one of four categories: **Supervised resources**, **Capacity**, **Scheduling and allocation**, **Repeated requests**. Editing one category preserves the other settings. See [the configuration guide](CONFIGURATION_UI_v1.1-rc2.md).

Existing queues without a capacity mode remain Classic, and old service calls remain compatible.

## Weighted request example

Given a weighted queue with total capacity 100 and a default weight of 30 units for the living-room entity:

    action: resource_queue_manager.request
    data:
      config_entry_id: YOUR_CONFIG_ENTRY_ID
      resource_id: heater_living_room
      entity_id: light.heater_living_room

For a one-request override of 25 units:

    action: resource_queue_manager.request
    data:
      config_entry_id: YOUR_CONFIG_ENTRY_ID
      resource_id: heater_living_room
      entity_id: light.heater_living_room
      engine_data:
        weight: 25

A request's effective weight is frozen while waiting, active, and after restart. An otherwise identical repeated request that omits an override retains its previous frozen weight. Explicit attempts to change existing weights fail. Invalid and unknown provider fields are rejected.

Classic accepts no nonempty engine_data. A pending request consumes no units; only active reservations consume capacity. With the default **Strict** allocation mode, if the first pending request cannot fit, later requests cannot skip it. Optional **Backfill** may grant later requests that fit remaining units, without changing the blocked request's order.

A queue cannot switch capacity mode with active or pending requests. Its unit budget cannot be reduced below committed active usage or a pending request's frozen weight. Every reload starts paused and requires explicit resume.

## Scope

The v1.1 implementation preserves the four existing sensor IDs. In Weighted mode, the Available sensor reports remaining **units**, not free slots; attributes include `capacity_mode`, `capacity_unit`, `capacity_total`, `capacity_used`, `capacity_remaining`, `effective_weights`, `allocation_mode`, `recurrence_mode` and `occurrence_counts`. Grant events expose effective weight and occurrence count. RQM never switches physical equipment directly.
