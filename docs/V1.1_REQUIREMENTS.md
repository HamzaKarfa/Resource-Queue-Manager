# Resource Queue Manager v1.1.0 — Requirements and delivery plan

Status: **implemented in stacked draft PRs; pending review, migration validation and explicit v1.1 release approval**. Baseline: v1.0.0. This specification does **not** describe published features.

Implementation sequence: [#19](https://github.com/HamzaKarfa/Resource-Queue-Manager/pull/19) classic foundation → [#20](https://github.com/HamzaKarfa/Resource-Queue-Manager/pull/20) weighted → [#21](https://github.com/HamzaKarfa/Resource-Queue-Manager/pull/21) HA settings → [#22](https://github.com/HamzaKarfa/Resource-Queue-Manager/pull/22) recurrence → [#23](https://github.com/HamzaKarfa/Resource-Queue-Manager/pull/23) action/sensor/event contracts → [#24](https://github.com/HamzaKarfa/Resource-Queue-Manager/pull/24) migration guards. See the v1.1 release checklist for acceptance and remaining live-HA checks.

## Objectives

Extend Resource Queue Manager while preserving all existing queues and automations:

1. Keep **one reservation engine** coordinating requests, active reservations, persistence, and supervision.
2. Keep the existing **FIFO, LIFO, and Priority FIFO** strategies for ordering waiting requests.
3. Introduce an independent, provider-based **capacity policy**: `classic` (slots) or `weighted` (units).
4. Introduce optional **recurrence counting** for repeated pending requests, without duplicating queue entries.
5. Keep Home Assistant device control entirely within the user's automations.

## Architecture

- **Scheduling strategy**: orders pending request IDs; never grants capacity or preempts active work.
- **Capacity policy**: calculates usage, decides whether the next queued request fits, validates restored capacity, and exposes capacity metrics.
- **Recurrence policy**: decides whether an identical pending `resource_id` increments an occurrence count.
- **Core engine**: owns queue state transitions, persistence-safe snapshots, strict head-of-line allocation, and coordination of the policies.
- **Home Assistant adapter**: config flow, entity supervision, action schema, sensors, events, recovery and persistent storage.

Plugins remain pure Python and explicitly registered. Providers may declare queue-level, per-entity and per-request fields using validated descriptors. No provider dynamically loads untrusted modules or controls a device.

## F01 — Classic capacity mode

- `classic` is the default for old and new queues.
- Queue capacity remains the maximum number of simultaneous active reservations (`max_active`).
- Each reservation consumes exactly one slot.
- Current `active`, `waiting`, `available` and `status` sensors and legacy service calls preserve their behavior.
- No existing configuration or snapshot needs modification.

## F02 — Weighted capacity mode

- `weighted` uses a queue-wide integer `capacity` expressed in generic units, **not watts**.
- There is **no second active-slot limit** in weighted mode.
- Every supervised `entity_id` has a **default integer weight**, initially 1, configurable in the integration's options.
- A request without `engine_data` uses its entity's configured default weight.
- Optional `engine_data.weight` overrides that default **for this request only**, never the entity's saved setting.
- The resolved effective weight is recorded at creation and remains unchanged through waiting, grant, release and restart, even if the entity's default changes.
- Only positive integers are valid. Reject booleans, fractions, non-finite values and weight greater than total capacity.
- Admission condition: `sum(active effective weights) + candidate effective weight <= total capacity`.
- A released reservation returns exactly its effective weight. Pending requests consume zero units.
- Updating an entity default affects **future new requests only**. Removing an entity still bound to any pending/active request is prohibited.
- Reject configuration changes that would invalidate active usage or make existing pending weights impossible to grant; switching capacity mode with nonempty state remains prohibited.

## F03 — Scheduling + allocation

All six combinations are supported: `fifo|lifo|priority_fifo` x `classic|weighted`.

- Scheduling strategies determine pending order; capacity policies never reorder requests.
- **Strict head-of-line**: if the first waiting request cannot fit, the allocator stops. A smaller later request does not skip ahead.
- Existing active grants are non-preemptive.
- When a release makes the first pending request fit, grant it, then continue in strategy order until the next does not fit.
- Duplicate requests must not move their place, change priority, or increase effective weight.

## F04 — Recurrence mode

- `ignore` (default) retains v1.0 idempotence.
- `count` tracks repeated **pending** requests with the **same `resource_id`**; one pending entry, occurrence count begins at 1.
- Identical re-request while pending increments the count; no new slot or units are consumed; the queue position, priority and effective weight remain unchanged.
- Re-request for an **active** resource does not increase the count or reserve another slot.
- An explicit attempt to change priority or effective weight of an existing request must be rejected rather than silently rewritten. A request that omits the optional weight override remains idempotent even if the entity default changed after its creation.
- Upon grant, the occurrence count is available to the automation in the grant event and sensors; release/cancel removes it.
- Counts survive restart. Duplicate detection is strictly by `resource_id`, **not message text or payload equality**.
- Counting does not execute or queue multiple jobs; it annotates a single request only.

## F05 — Action and API contract

Legacy request actions remain valid. For weighted queues:

```yaml
action: resource_queue_manager.request
data:
  config_entry_id: YOUR_CONFIG_ENTRY_ID
  resource_id: heater_living_room
  entity_id: light.heater_living_room
  strategy_data:
    priority: 8
  engine_data:
    weight: 25
```

- `strategy_data`: validated only against the chosen scheduling strategy.
- `engine_data`: optional; validated only against the chosen capacity provider.
- Queue and per-entity capacity fields live in config entry options, with localized native Home Assistant selectors.
- Invalid or unknown provider fields fail explicitly.
- No new device-switching action is introduced.

## F06 — Sensors, events and persistence

- Keep the four current per-entry sensor IDs unchanged. Their existing meanings stay unchanged in classic mode.
- Expose `capacity_mode` and explicit `capacity_total`, `capacity_used`, `capacity_remaining` fields; distinguish generic **units** from active request **count**.
- Expose per-request effective weights and occurrence counts through attributes, and add occurrence count to the appropriate grant event payload.
- Preserve ID-only `active` and `waiting` lists for existing automation templates.
- Save provider mode/config, per-entity default weights, effective per-request weights, occurrence mode/counts, strategy metadata and entity bindings.
- Legacy v1.0 snapshots lacking new keys restore as `classic + ignore`.
- Each queue continues to start `paused` on restart/reload; snapshots must not generate new grants during loading.
- In weighted mode, a restored queue may legitimately contain pending work with nonzero free units (head-of-line blocked).
- Retain serialized state locking, disk-write-before-grant-event semantics, and independent config entries.
- A corrupt/unsafe snapshot must fail closed; do not silently drop active reservations.

## F07 — Compatibility, validation and scope

**Required test coverage**

- Current v1.0 unit/HA integration tests pass unchanged.
- Capacity provider registry, invalid options, and classic equivalence.
- Weighted allocation under FIFO/LIFO/Priority FIFO, strict head-of-line and no preemption.
- Entity defaults, optional override, immutable effective weight, duplicate-with-omitted-override semantics.
- Recurrence counting in waiting only, no reorder, restoration, cancellation and event payload.
- Legacy snapshot migration, paused/recovery semantics, multiple independent queues and config modifications.
- Native HA setup/options screens, translation keys, service validation, status/metric compatibility.

**Out of scope**

Electrical power measurement, load shedding, automatic device switching, message-content deduplication, multi-job execution against one supervised entity, dynamically changing an active request's weight/priority, and backfilling past blocked requests.

## Implementation sequence

1. Introduce provider-backed `classic` capacity policy with zero functional behavior change.
2. Add weighted capacity policy and frozen per-request effective weights, with unit tests.
3. Add provider-driven Home Assistant mode and per-entity default-weight configuration.
4. Add optional recurrence counting and persistence.
5. Integrate new action data, sensors, grant event metadata and migration guards.
6. Run HA integration tests, update EN/FR documentation, validate upgrade and cut an explicitly approved release.

Each implementation stage gets a focused PR and is merged only after relevant tests and review. No automatic release is triggered.
