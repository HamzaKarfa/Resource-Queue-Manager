# Resource Queue Manager — v1.1.0

**Stable release** — the v1.1 capabilities were validated in the [v1.1.0-rc.2 release candidate](https://github.com/HamzaKarfa/Resource-Queue-Manager/releases/tag/v1.1.0-rc.2). This release keeps v1.0 automations compatible while adding weighted budgets, Backfill, recurrence counting and improved Home Assistant configuration.

## Overview

Version 1.1 adds **four independent controls for each resource queue**: scheduling order (FIFO/LIFO/Priority FIFO), capacity (Classic/Weighted), allocation (Strict/Backfill), and repeated requests (Ignore/Count). Each configuration entry keeps its own reservations, sensors, policy choices and persistent state.

### Capacity

- **Classic** remains the default: between 1 and 50 simultaneous reservations.
- **Weighted** uses a total of 1–100000 shared integer units with **no second active-slot limit**. Supervised entities have integer default weights (initially 1).
- Optional `engine_data.weight` temporarily overrides the weight of a **new request only**. It does not modify the entity default; a request's resolved weight is frozen through waiting, grant and restart.

### Admission: Strict / Backfill

- **Strict**, the default and backwards-compatible mode, stops allocation at the first pending request that does not fit.
- **Backfill** may grant later requests that fit remaining capacity while retaining blocked requests' original order and frozen metadata.
- No preemption or overcommit. A large or high-priority request can be starved by recurring smaller requests; no fairness/aging mechanism is included.

### Repeated requests

- **Ignore**, the default, preserves idempotent waiting requests.
- **Count** increments the occurrence counter for identical requests with the same **waiting** `resource_id`, without duplicating entries, changing priority or consuming extra units. Already-active requests are idempotent.
- Event payloads and sensor attributes expose occurrence counts. These are metadata, **not automatic repeated executions**.

### Home Assistant integration

- Guided first setup with conditional per-entity weight and priority-direction screens.
- **Configure** presents four independent categories: Supervised resources, Capacity, Scheduling and allocation, Repeated requests.
- Editing one category preserves the others. Opening the menu does not pause a running queue. Accepted changes keep normal reload/paused recovery.
- The four existing sensor entity IDs are retained; new attributes include `capacity_mode`, `capacity_unit`, `capacity_total`, `capacity_used`, `capacity_remaining`, `effective_weights`, `allocation_mode`, `recurrence_mode` and `occurrence_counts`.
- Persisted grant events include `capacity_mode`, `allocation_mode`, frozen `effective_weight` and `occurrences`.
- Native forms and help text are available in English and French.

### Recovery and compatibility

- Existing v1.0 queues without new fields default to **Classic + Strict + Ignore**; action YAML, strategy priority semantics and existing sensor IDs remain valid.
- Every queue still reloads **paused**; safely inspect supervised entities and call `resume` explicitly.
- Invalid persisted weights, bindings, unknown policies or recurrence counts fail closed instead of discarding bookings. Grants are announced only after successful persistence.
- Independent queues still require `config_entry_id` in all actions when two or more entries exist.

## What is not included

No physical device switching, electrical power measurement, global load limit across queues, automatic priority aging or anti-starvation logic, message-content-based deduplication, and no automatic execution of multiple jobs from one counted request.

## Updating and rollback

**Home Assistant 2026.11.0 or later is required.** Back up the full Home Assistant configuration and relevant `.storage` state first. After an upgrade, review saved active/waiting reservations and the physical ON/OFF state of supervised equipment before `resume`.

A code-only downgrade after using Weighted or Count snapshots is **not guaranteed**; use a matching full backup (code, config entries and stored reservations). See the [migration guide](../MIGRATION_v1.0_to_v1.1.md).

## Verification and limitations

Automated checks for Python 3.13/3.14, Home Assistant 2026.11, HACS and hassfest are required on the exact stable merge commit before publication. The project’s fixture tests do not substitute for an independent live Home Assistant migration/backup restoration rehearsal. **Make a backup before upgrading**, especially if physical ON/OFF entities are involved.

For complete instructions, see [README](../../README.md), [French README](../../README.fr.md), [migration guide](../MIGRATION_v1.0_to_v1.1.md) and [Backfill details](../V1.2_BACKFILL.md).

Resource Queue Manager operates only on logical reservations; it is **not** an electrical safety device, protection relay, power meter or certified load shedder.
