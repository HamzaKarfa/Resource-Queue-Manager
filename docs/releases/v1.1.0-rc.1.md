# Resource Queue Manager — v1.1.0-rc.1

**Release candidate / préversion : pour essais, pas encore une version stable.**

Cette préversion intègre l'ensemble des développements #19 à #25, sans fusion sur `main`. Elle est destinée à valider la compatibilité, la restauration d'état et les nouvelles fonctions sur une instance Home Assistant de test avant une éventuelle version stable v1.1.0.

## Nouveautés

- **Trois responsabilités indépendantes** : stratégie FIFO/LIFO/Priority FIFO, politique de capacité `classic`/`weighted`, récurrence `ignore`/`count`.
- **Mode pondéré** : un budget unique d'unités entières, sans limite supplémentaire de places. Poids par défaut configurable pour chaque entité supervisée, initialement 1.
- **Override par demande** : `engine_data.weight` ajuste le poids uniquement pour une nouvelle réservation, figé pendant l'attente, l'activité et après redémarrage.
- **Récurrences** : `count` cumule les demandes répétées d'un même `resource_id` **en attente**, sans créer d'entrées supplémentaires ; une réservation déjà active n'incrémente pas son compteur.
- **Capteurs** : les quatre entités historiques sont conservées et ajoutent des attributs `capacity_mode`, `capacity_unit`, `capacity_total`, `capacity_used`, `capacity_remaining`, `effective_weights`, `recurrence_mode` et `occurrence_counts`.
- **Événements d'attribution** : ajout de `capacity_mode`, `effective_weight` et `occurrences`, avec sauvegarde de l'état avant la notification.
- **Restauration** : compatibilité des snapshots anciens `classic + ignore`, arrêt prudent en cas de données incompatibles, reprise `paused` jusqu'à un `resume` explicite.

## Compatibilité

Les automatisations classiques v1.0 existantes conservent les quatre services `request`, `release`, `cancel`, `resume` et leurs paramètres. Les stratégies FIFO/LIFO/Priority FIFO et les règles d'observation OFF ne changent pas. Aucun contrôle direct des appareils n'est ajouté.

Les modes pondéré et comptage sont optionnels. Une modification de politique avec une file non vide est refusée. En mode pondéré, une demande plus petite ne double jamais une demande prioritaire qui ne rentre pas dans les unités disponibles.

## Exemple

```yaml
action: resource_queue_manager.request
data:
  config_entry_id: YOUR_QUEUE_ENTRY_ID
  resource_id: garage_notice
  entity_id: input_boolean.queue_notice
  engine_data:
    weight: 25
```

`engine_data.weight` est disponible **uniquement** pour une file pondérée, et les unités sont génériques (pas nécessairement des watts). Si la file utilise `count`, les répétitions du même `resource_id` encore en attente sont regroupées.

## Installation / essais

Tester de préférence sur une instance Home Assistant 2026.11+ séparée. Sauvegarder la configuration et les fichiers `.storage`, utiliser le dossier complet `custom_components/resource_queue_manager` de cette préversion, puis redémarrer. Contrôler les réservations actives/en attente, les états des entités supervisées, le capteur `status` en pause, et reprendre explicitement la file.

**Rollback :** revenir à v1.0 avec la sauvegarde correspondante (code, entrées de configuration et données persistées), pas en remplaçant simplement le code après utilisation de nouveaux modes.

Voir [le guide de migration](../MIGRATION_v1.0_to_v1.1.md), [la checklist de validation](../RELEASE_CHECKLIST_v1.1.md) et [les spécifications](../V1.1_REQUIREMENTS.md).

Cette préversion ne prétend ni garantir la sécurité électrique, ni piloter les équipements directement. **Elle ne remplace aucune protection matérielle.**
