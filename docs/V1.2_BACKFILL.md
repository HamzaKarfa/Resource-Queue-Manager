# Resource Queue Manager — Backfill allocation mode (unreleased)

**Status: draft feature, not included in the immutable v1.1.0-rc.1 pre-release.** No release/production deployment is triggered by this branch.

## Independent scheduling, capacity and allocation

The v1.1 queues use three independent settings already: scheduling (FIFO/LIFO/Priority FIFO), capacity (classic or weighted) and duplicate handling (ignore or count). This change introduces a fourth, **allocation mode**:

- `strict` **(default)** — stop when the first waiting request cannot fit remaining capacity. Existing v1.0/v1.1 snapshots and configurations retain exactly this behavior.
- `backfill` — scan waiting requests in the order selected by FIFO, LIFO or Priority FIFO, and grant each candidate that fits. Blocked requests retain their relative ordering, metadata and recurrence count.

The mode applies to each integration config entry independently. It can be selected at queue creation or in Settings → Devices & services → Resource Queue Manager → Configure. **Switching modes requires an empty queue** (no active or waiting requests), like switching capacity policies.

## Example — 15 units

| Resource | Weight | Strict mode | Backfill mode |
|---|---:|---|---|
| A already active | 10 | Active | Active |
| B first in waiting order | 10 | Waiting | Waiting |
| C next | 3 | Waiting | **Granted** |
| D next | 2 | Waiting | **Granted** |

Strict mode keeps 5 unused units. Backfill grants C and D, uses all 15 units, and **keeps B first among the waiting IDs**. When A releases 10 units, B can receive a grant, provided capacity remains available.

With **Priority FIFO**, a high-priority request that cannot fit can be bypassed by a lower-priority request that fits. Among requests that fit, Priority FIFO's order (including FIFO ties) is preserved, but backfilling can lead to starvation of a high-weight request when smaller requests arrive continuously.

## Guarantees and limitations

- No preemption, forced release, device switching, bypass of OFF confirmation or capacity overcommit.
- Effective weights and recurrence counts remain frozen/persisted exactly as before. A repeated waiting ID does not move forward or backward and does not change its effective weight.
- Capacity mode `classic` is supported, but all classic reservations cost one slot so strict and backfill will normally behave the same.
- `allocation_mode` is persisted in each queue snapshot and exposed on the existing four sensors and in grant-event data. Absent keys restore as `strict`; unrecognized keys fail closed.
- **No aging/reservation of future units, fairness quota or starvation prevention in this initial iteration.** Choosing backfill trades strict ordering for better utilization. Do not imply that priority alone guarantees service.
- Each queue still starts `paused` after restart or configuration update, and requires a checked `resume`. All release/cancel safety checks remain unchanged.

## Example Home Assistant sensor attributes

```yaml
capacity_mode: weighted
allocation_mode: backfill
strategy: priority_fifo
recurrence_mode: count
capacity_total: 15
capacity_used: 15
capacity_remaining: 0
active: [a, c, d]
waiting: [b]
effective_weights:
  a: 10
  b: 10
  c: 3
  d: 2
```

This example shows logical grants only. The integration does not actuate physical devices.
