# Recurrence counting — Resource Queue Manager v1.1

The optional **Recurrence mode** is independent of scheduling (FIFO, LIFO, Priority FIFO), capacity (Classic/Weighted) and allocation (Strict/Backfill). Existing v1.0 configurations and automations continue in **Ignore** mode by default. Included in the published **v1.1.0-rc.2 pre-release**, this behavior is prepared for the upcoming v1.1.0 stable release.

## Modes

- `ignore` (default): a repeated `resource_id` is idempotent. No new queue entry or occurrence increment.
- `count`: a repeated **pending** `resource_id` increments its counter. There is still exactly one waiting entry, with unchanged priority, frozen effective weight and position. A repeated **active** request remains idempotent and does not increment the counter.

A new request begins with `occurrences = 1`. The counter follows it when granted and survives integration reloads. A subsequent cancel or release removes the counter. A new request under the same `resource_id` starts again at 1.

Duplicates are detected **only by `resource_id`**, not by TTS text, message content, origin, or event payload. The original entity binding and request metadata must still match. Attempts to modify an existing request's strategy priority or effective capacity weight fail explicitly, without incrementing the counter.

## Example: aggregate announcements

Configure a queue with capacity 1, recurrence mode `count`, and supervise the logical entity used for your TTS automation. Suppose one announcement has an active grant:

    action: resource_queue_manager.request
    data:
      config_entry_id: YOUR_QUEUE_ID
      resource_id: tts_garage
      entity_id: input_boolean.tts_gate

If `tts_garage` is *waiting*, repeating the same request three times yields **one waiting request with occurrences = 3**. When it receives capacity, the grant event contains:

    event_type: resource_queue_manager_slot_granted
    data:
      config_entry_id: YOUR_QUEUE_ID
      resource_id: tts_garage
      entity_id: input_boolean.tts_gate
      occurrences: 3

The integration never speaks, actuates equipment or executes three separate jobs: your automation decides whether to synthesize a single announcement mentioning the count.

All four existing sensors keep their IDs and states. The extra attributes include:

    recurrence_mode: count
    occurrence_counts:
      tts_garage: 3

The counters include *active and waiting* resources, even after a grant. A recurrence update is serialized with the queue store write before dispatching sensor updates and grant events.

## Compatibility and safety

- Changing recurrence mode requires the queue to be empty (no active and no waiting requests).
- Existing snapshots without recurrence metadata restore as `ignore` with each request count set to 1.
- Count-mode snapshots missing or containing invalid recurrence metadata fail closed: active reservations are never silently dropped.
- As before, each queue starts **paused** after reload and must be explicitly resumed.
- This mode has no effect on ordering, priority, allocations, or physical ON/OFF supervision.
